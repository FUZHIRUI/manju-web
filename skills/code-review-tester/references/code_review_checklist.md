# 代码审查清单

## 1. 代码风格与规范

### 1.1 命名规范
- [ ] 变量名使用 snake_case（Python）
- [ ] 函数名使用 snake_case（Python）
- [ ] 类名使用 PascalCase（Python）
- [ ] 常量名使用 UPPER_SNAKE_CASE
- [ ] 命名具有描述性，避免使用缩写（除非是广泛认知的）
- [ ] 布尔变量使用 is/has/can 等前缀（如 is_valid, has_permission）

### 1.2 代码格式
- [ ] 缩进使用 4 个空格（Python）
- [ ] 行长度不超过 120 字符
- [ ] 函数之间有适当的空行
- [ ] 运算符周围有空格
- [ ] 逗号后有空格
- [ ] 文件末尾有一个空行

### 1.3 导入规范
- [ ] 导入按顺序分组：标准库、第三方库、本地模块
- [ ] 每组导入之间有空行
- [ ] 不使用通配符导入（from module import *）
- [ ] 导入语句在文件顶部

### 1.4 注释与文档
- [ ] 复杂逻辑有清晰的注释说明
- [ ] 注释解释"为什么"而不是"做什么"
- [ ] 公共函数/类有 Google 风格的 docstring
- [ ] docstring 包含参数说明、返回值说明、异常说明
- [ ] 过时的代码已删除，而不是注释掉

## 2. 代码质量

### 2.1 单一职责
- [ ] 每个函数只做一件事
- [ ] 每个类只有一个改变的理由
- [ ] 函数/类长度适中（不超过 50 行）

### 2.2 可读性
- [ ] 代码逻辑清晰，易于理解
- [ ] 避免过深的嵌套（不超过 3 层）
- [ ] 复杂条件抽取为有意义的变量
- [ ] 魔法数字替换为命名常量

### 2.3 可维护性
- [ ] 代码结构合理，模块划分清晰
- [ ] 依赖关系简单，避免循环依赖
- [ ] 配置项集中管理，不硬编码
- [ ] 遵循 DRY 原则，无重复代码

### 2.4 可扩展性
- [ ] 预留扩展点，便于未来功能扩展
- [ ] 使用组合优于继承
- [ ] 接口设计稳定，避免频繁变更

## 3. 类型注解

### 3.1 函数签名
- [ ] 所有函数参数都有类型注解
- [ ] 所有函数都有返回值类型注解
- [ ] 使用 typing 模块的类型（List, Dict, Optional 等）
- [ ] 复杂类型使用类型别名提高可读性

### 3.2 类型安全
- [ ] 避免使用 Any 类型
- [ ] Optional 类型正确处理 None 值
- [ ] 集合类型指定元素类型

## 4. 错误处理

### 4.1 异常处理
- [ ] 捕获具体的异常类型，不使用裸 except
- [ ] 异常信息清晰，包含上下文
- [ ] 资源正确释放（使用 with 语句）
- [ ] 不吞掉异常，必要时重新抛出

### 4.2 输入验证
- [ ] 对用户输入进行验证
- [ ] 边界条件处理正确
- [ ] 空值检查完善
- [ ] 类型转换安全

## 5. 安全性

### 5.1 敏感信息
- [ ] 密码、密钥不硬编码
- [ ] 敏感信息从环境变量或配置文件读取
- [ ] 日志不记录敏感信息
- [ ] 错误信息不暴露内部细节

### 5.2 数据安全
- [ ] SQL 查询使用参数化，避免注入
- [ ] 外部输入正确转义
- [ ] 文件路径验证，防止路径遍历
- [ ] 权限检查完善

## 6. 性能

### 6.1 算法效率
- [ ] 避免不必要的循环
- [ ] 使用合适的数据结构
- [ ] 避免在循环中做昂贵的操作
- [ ] 缓存频繁使用的计算结果

### 6.2 I/O 操作
- [ ] 文件操作使用上下文管理器
- [ ] 批量操作优于单次操作
- [ ] 合理使用异步 I/O（如需要）
- [ ] 数据库查询避免 N+1 问题

## 7. 测试

### 7.1 可测试性
- [ ] 函数/类设计易于测试
- [ ] 依赖注入，便于 mock
- [ ] 纯函数优先
- [ ] 副作用明确

### 7.2 测试覆盖
- [ ] 核心功能有测试覆盖
- [ ] 边界条件有测试
- [ ] 异常情况有测试
- [ ] 测试用例描述清晰

## 8. 日志

### 8.1 日志规范
- [ ] 使用合适的日志级别（DEBUG/INFO/WARNING/ERROR）
- [ ] 日志信息包含关键上下文
- [ ] 结构化日志格式（JSON）
- [ ] 包含请求 ID/Trace ID

### 8.2 日志内容
- [ ] 关键业务流程有日志
- [ ] 错误日志包含堆栈信息
- [ ] 不记录敏感信息
- [ ] 日志量适中，不过度也不缺失

## 审查结论

- [ ] 通过 - 代码质量良好，可以合并
- [ ] 有条件通过 - 需要修复以下问题后合并
- [ ] 不通过 - 需要重大改进后重新审查
